# Модуль ККД — страница контроля качества данных по целям

Тестовое задание Frontend: страница модуля ККД поверх готового
[mock API](https://gitverse.ru/kkk_s/moc_api_kkd). Руководитель с первого взгляда видит,
стало ли лучше или хуже по сравнению с прошлым прогоном и что исправлять первым.

**Стек:** React 18 + TypeScript + Ant Design 5, сборка Vite, тесты Vitest. Визуал — по `UI-KIT.md` из репозитория mock API.

## Запуск

Нужен Docker. Поднимаются и страница, и mock API (он собирается прямо из своего git-репозитория):

```bash
git clone https://github.com/draharle/sber-goal-tracker-frontend.git kkd-frontend
cd kkd-frontend
docker compose up --build
```

Страница — http://localhost:8080, mock API — http://localhost:8000/docs.

### Без Docker

Нужны Node.js 20.19+ и Python 3.11+.

```bash
# 1. mock API — в папке его репозитория
pip install -r requirements.txt && uvicorn app.main:app --port 8000

# 2. страница — в папке этого репозитория, в другом терминале
npm install
npm run dev          # http://localhost:5173, запросы /api проксируются на localhost:8000
```

Другие команды: `npm test` — тесты, `npm run build` — сборка с проверкой типов, `npm run preview` — посмотреть сборку.

### Переменные окружения

Все необязательные, образец — `.env.example`.

| Переменная | Где работает | Зачем |
|---|---|---|
| `API_PROXY_TARGET` | `npm run dev` | Куда dev-сервер проксирует `/api`. По умолчанию `http://localhost:8000`. В Docker то же делает nginx, адрес задан в `docker-compose.yml` |
| `VITE_API_URL` | сборка | Адрес API для браузера. Пусто — тот же адрес, что у страницы (через прокси). Можно указать `http://localhost:8000`: у mock API открыт CORS |
| `FRONTEND_PORT` | docker compose | Порт страницы, по умолчанию 8080 |

## Что на странице

1. **Шапка** — подразделение (дерево из `/api/meta`) и прогон (`/api/runs`, упавший помечен «ошибка»).
2. **Контекст** — путь подразделения и строка «Сравнение с RUN-007 от 26.10.2026» или «Первый прогон — сравнивать не с чем».
3. **Метрики** — четыре главные крупно, остальные компактно: значение, было, дельта со стрелкой и отдельно оценка «Лучше / Хуже».
4. **Найденные проблемы и дельта** — счётчики «Новые / Сохраняются / Исправлены» и «Что исправлять первым»
   по важности и правилам. Всё кликабельно и открывает таблицу с фильтром.
5. **Список проблем** — фильтры по правилу, важности, статусу дельты, сортировка, серверная пагинация.
6. **Карточка проблемы** — модальное окно: что не так, факт и ожидание, как исправить, история по прогонам.

Состояние выбора хранится в адресе (`?unit=CIB-REG&run=RUN-008&status=new&issue=…`): ссылку можно отправить коллеге.

## Граничные состояния

| Случай | Что видит пользователь |
|---|---|
| Первый прогон RUN-001 (`previous`, `delta` = `null`) | «Нет данных для сравнения» в карточках, «Первый прогон — сравнивать не с чем» в шапке, объяснение вместо счётчиков дельты |
| Упавший прогон RUN-006 (409 `RUN_FAILED`) | Причина из API и кнопки «Открыть RUN-007» / «Открыть RUN-005». Запрос не отправляется: статус известен из списка прогонов; если API всё же ответит 409 — тот же экран |
| RUN-007 сравнивается с RUN-005 | Рядом с «Сравнение с RUN-005»: «RUN-006 пропущен: завершился с ошибкой» |
| Подразделение без целей TX-NEW (метрики `null`) | Пустое состояние «нет активных целей — это не 0 проблем» и переход к вышестоящему подразделению |
| Загрузка (у API задержка 300 мс) | Скелетоны; при смене страницы таблицы старые строки со спиннером; через 3 с — «Сервер отвечает дольше обычного» |
| Ошибка сети, API не запущен | Блок ошибки и «Повторить»; через 15 с без ответа — «Сервер отвечает слишком долго» |
| Пустой результат фильтра | «По выбранным фильтрам проблем нет» и «Сбросить фильтры» |
| Испорченная ссылка | Мусорные параметры отбрасываются; неизвестный прогон или подразделение — «не найдено» и кнопка вернуться к блоку |

## Устройство

```
src/
  api/          типы ответов, fetch-обёртка, пути эндпоинтов, кэш запросов
  hooks/        useApiQuery (данные из API), usePageState (состояние в адресе)
  lib/          чистые функции: формат чисел и дельты, разбор адреса, дерево подразделений, прогоны (+ тесты)
  components/   шапка, карточки метрик, блок «что исправлять», таблица, карточка проблемы, теги, состояния
```

## Как объяснить на собеседовании

**Простыми словами.** Раз в неделю система проверяет цели сотрудников по правилам: есть ли ключевые результаты,
сходятся ли веса, привязана ли цель к вышестоящей и т. д. Каждая такая проверка — «прогон». Моя страница показывает
результат прогона руководителю. Сверху — метрики: например, какая доля целей без ошибок, и как она изменилась
с прошлого прогона. Ниже — что исправлять первым: сначала критичные проблемы, потом остальные. Ещё ниже — список
самих проблем с фильтрами, а по клику — карточка: что не так, как должно быть и как исправить. Все числа приходят
из API, страница их только показывает — сама ничего не считает. Главное, о чём я думал: не обмануть руководителя.
Если сравнивать не с чем — так и пишу, а не рисую ноль. Если число выросло, это ещё не значит «хорошо» —
оценку беру из поля `trend`.

**Вопросы и ответы**

1. **Почему знак дельты — это не «лучше / хуже»?**
   Рост доли корректных целей — хорошо, а рост числа проблем — плохо, хотя у обоих знак плюс. Поэтому стрелка
   показывает только направление числа, а цвет и слово «Лучше / Хуже» берутся из поля `trend`, которое считает API
   с учётом `higher_is_better`. Если у метрики нет «хорошего» направления (например, «Активные цели»), пишу «Без оценки».

2. **Почему `null` нельзя показывать как 0?**
   Ноль — это измерение: «проблем ноль». `null` — измерения нет: первый прогон, сравнивать не с чем, или в подразделении
   нет целей. Если нарисовать 0, руководитель решит, что всё стабильно или всё идеально. Поэтому пишу «Нет данных для
   сравнения», а для подразделения без целей — отдельный экран «целей нет, это не 0 проблем».

3. **Зачем хранить выбор в адресной строке?**
   Чтобы смена подразделения, прогона и фильтров шла без перезагрузки, работала кнопка «Назад» и можно было
   скинуть коллеге ссылку на ту же картину, вплоть до открытой карточки. Последний прогон подставляю в адрес явно —
   иначе через неделю ссылка «последний» покажет другие данные.

4. **Как вы избегаете дублирования запросов?**
   У каждого запроса ключ — его путь с параметрами. Пока запрос по ключу идёт или уже выполнен, повторный не уходит,
   а результат берётся из кэша: данные завершённого прогона не меняются. Когда пользователь быстро щёлкает фильтры,
   ненужный уже запрос отменяется через `AbortController`. Отмену откладываю на один тик, чтобы StrictMode в React,
   который монтирует компонент дважды, не отправлял запрос два раза.

5. **Почему не React Query?**
   Нужны были три вещи: не дублировать, отменять устаревшее, кэшировать. Это около 150 строк без зависимостей,
   и их легко объяснить. React Query решил бы то же, но тянет то, что тут не нужно. В большом проекте я бы взял его.

6. **Как собрана тема?**
   Тему из `UI-KIT.md` скопировал в `theme.ts` и подключил одним `ConfigProvider`. Компоненты берут цвета через
   `theme.useToken()`, а для своих CSS-стилей нужные токены попадают в CSS-переменные. В итоге hex-цвета есть только
   в одном файле: поменялся кит — правится один файл.

7. **Что будет с упавшим прогоном RUN-006?**
   API на него отвечает 409 `RUN_FAILED`. Статус прогона я знаю заранее из списка прогонов, поэтому лишний запрос
   не отправляю, а сразу пишу причину и предлагаю открыть соседние успешные прогоны. Если статус поменялся и пришёл
   409 — показывается тот же экран. И если RUN-007 сравнивается с RUN-005, пишу, что RUN-006 пропущен.

8. **Как цвет не остаётся единственным носителем смысла?**
   У важности — тег со словом и своим значком, у статуса дельты — тоже. У дельты — стрелка и число со знаком,
   у оценки — слово и значок. Для текста беру «текстовые» оттенки из кита, чтобы контраст был не меньше 4.5:1.

9. **Что покрыто тестами?**
   Чистые функции без React: формат дельты и единиц (проценты → п.п.), оценка из `trend`, различие `null` и 0,
   разбор адреса и пагинация `limit/offset`, дерево подразделений, пропущенные прогоны, порядок «что исправлять первым»,
   разбор ошибок API. Интерфейс проверял вручную по критериям приёмки из `specs/requirements.md`.

10. **Что бы вы сделали дальше?**
    Мини-график динамики доли корректных целей по прогонам (`/api/kkd/trend`) прямо в карточке — с разрывом на
    упавшем прогоне, поиск по проблемам, выгрузку в CSV и компонентные тесты на граничные состояния.
